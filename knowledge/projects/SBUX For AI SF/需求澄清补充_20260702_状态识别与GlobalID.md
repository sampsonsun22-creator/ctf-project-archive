# 需求澄清补充（2026-07-02，口头澄清，并入 BRD v2）

## 澄清内容（来自项目侧）

1. **SSP Submitted 状态无法从 EP 上传数据中用规则识别**。它由星巴克新店计划管理的**线下子流程**决定（是否已提交董事会），EP 里没有任何字段组合能推导出来。
2. 店号（Global ID）来自**另一条子流程**（店号申请）。有的新店在提交董事会前该子流程已走完（有店号），有的还没走完（无店号）；**店号子流程不影响新店计划是否提交董事会**。
3. 因此 **SSP Submitted 门店是混合人群：部分带 Global ID，部分不带**。

## 对 BRD 的修订影响

| 影响点 | v1 表述 | v2 修订 |
|---|---|---|
| Q4 数据源 | 待确认（SD 手工 vs DMP 同步）| **关闭**：状态只能由 SD 人工录入；系统不做自动识别/默认推导；DMP 同步不得覆盖手工状态 |
| Q2 特殊校验 | 待确认 | 半落定：特殊点＝①状态不可规则推导（无自动识别）②**Global ID 对 SSP Submitted 为可选** |
| 校验矩阵（FR-2.1）| 未提 Global ID 列 | 增列：SSP Submitted 的 Global ID＝可选。带店号→hierarchy 自 DMP 带出+走 Global ID 校验；不带→按 City 生成 Dummy ID |
| 状态机（FR-1）| 状态迁移未与店号解耦 | 显式声明：**状态轴与店号轴是两条独立生命周期**。店号可在任意状态下补录（Dummy→Global 绑定不触发状态变化）；状态迁移不要求店号变化 |
| FP 场景（FR-2.4）| 沿用金库口径 | 坐实：FP New Storelist 必须支持**带 Global ID** 的 SSP Submitted 店上传（金库记录 7.10 版曾强制"FP 新店不带 Global ID"、9.17 已去掉——需与系统侧确认当前实现兼容混合人群）|
| 风险 | 无此条 | 新增：**状态错标系统无法拦截**（无规则可校验真伪），只能靠 SD 录入 SOP+抽检；写入风险清单与操作手册 |
| 测试 | 单一路径 | SSP Submitted × {带 / 不带 Global ID} **两条子路径都要全流程测**（校验、hierarchy、storeday、RMIP、推 BI）|
